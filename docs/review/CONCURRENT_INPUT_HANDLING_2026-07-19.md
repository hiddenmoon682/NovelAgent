# 后续 Qt 前端设计参考：上一条任务未完成时用户输入新指令

> 记录日期：2026-07-19
> 相关：`QT_INTEGRATION_PLAN.md`、`BackendServer.cpp`、`Agent.cpp`

## 问题

当前架构中，Agent 处理一条用户消息是同步阻塞的（`processSerial`/`ToolCallLoop`）。加上 Qt 前端后，如果上一条任务还在执行（LLM 流式输出中 / 工具执行中），用户又输入了一条新指令，系统应该怎么处理？

## 当前防护

- **REPL 模式**：天然串行，`process()` 不返回就不会出现下一次输入
- **BackendServer 会话锁**（`Session::request_mutex`）：同一会话的并发请求串行化，第二个请求等第一个完成
- **状态机守卫**（`canAcceptInput()`）：Thinking/AwaitingTool 状态拒绝新输入

这三种防护在 Qt 前端下都可能被绕过——用户看到"任务还在跑"，不想等了，想发新指令中断当前任务。

## 设计思路

### 方案 A：取消当前任务（推荐）

```
用户发新输入 → 检查状态
  → Idle → 正常处理
  → Thinking/AwaitingTool → 取消当前任务 → 正常处理新输入
```

关键点：
1. 触发 `cancelled_` 原子标志 → ToolCallLoop 在当前轮结束后退出
2. 等待当前工具执行完再中断（不暴力杀线程）
3. 走已实现的"取消路径"：模拟终止记录到对话，通知 LLM
4. 然后处理新输入

需要在 Qt 前端加一个交互提示："当前有任务正在执行，是否取消并处理新指令？" 或直接静默取消。

### 方案 B：排队（按顺序执行）

```
用户发新输入 → 入队
  → 等当前任务完成 → 自动处理下一条
```

不需要额外前端交互，但用户不知道自己的指令什么时候被执行。

### 方案 C：并行会话（各聊各的）

```
用户发新输入 → 新建独立会话处理
  → 两个任务互不干扰
```

最复杂——共享 Project 需要读写锁，对话上下文各自独立。适合"让 AI 同时做两件事"的场景。

## 当前代码中已有的基础设施

- `cancelled_`（`ToolCallLoop.h:86`）：原子取消标志，已实现
- 取消后的对话终止记录（`ToolCallLoop.cpp:69-89`）：已实现
- `BackendServer` 的 `Session::request_mutex`：需要改造为"取消旧任务→接收新任务"而非阻塞等待
- `Agent::process()` 的状态守卫：需要调整——`Thinking` 状态也应允许输入（走取消），而非直接拒绝

## 建议

采用方案 A（取消当前任务）。Qt 前端实现前需要改造三个点：

1. `BackendServer`：收到新请求时，先发取消信号给当前执行中的 Agent，再处理新请求
2. `Agent::process()`：`Thinking`/`AwaitingTool` 状态不应直接拒绝输入，而是触发取消流程
3. 前端提示：告知用户上一条任务被中断，但对话中已保留了终止记录
